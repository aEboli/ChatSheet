本次改动包含三件事：修复面板「适配」的撤销与恢复报「找不到该操作记录」、

## 一、「适配」的撤销与恢复报「找不到该操作记录」

### 症状与现场

用户点面板「适配」，提示胶囊上出现「撤销」按钮，点下去却报
「找不到该操作记录，可能已超出保留范围」，恢复同样失败。

加载项日志里能完整看到这一幕：

```text
15:50:44 [INFO ] 适配 $A$1:$H$8：64 个单元格
15:50:45 [INFO ] 适配 $A$1:$H$8：64 个单元格
15:51:15 [INFO ] 撤销操作 fit-1e1253a1：失败 NOT_FOUND 找不到该操作记录，可能已超出保留范围。
15:51:16 [INFO ] 撤销操作 fit-5d478c61：失败 NOT_FOUND 找不到该操作记录，可能已超出保留范围。
15:51:17 [INFO ] 撤销操作 call_02_095e2e…：成功 已撤销：设置数字格式 Sheet1!$H$2:$H$8
```

关键在最后一行：同一个撤销栈里，模型调用留下的记录能正常撤销，只有适配的两条
找不到。撤销栈只在超过 60 条时丢弃最早的，这里远未触及，且被丢的会是更早那条。
所以那两条记录根本没有登记过——而面板却拿到了撤销标识。

### 成因

`fit_range` 允许省略 `range`，由工具自己取该表的已用范围，面板按钮正是这么调的。
但撤销快照必须在操作前采集，而当时的 `ToolExecutor.Execute` 直接拿参数里的
`range` 去采集：

```csharp
// 旧：参数里没有 range，采集直接放弃
before = TryCapture(args, detail);   // → null
if (before == null) { tracking = false; }   // → 不登记记录
```

于是 `TryCapture` 因为拿不到地址而返回 null，记录没有登记。
可 `sheet.fit` 通道仍然无条件回传了标识：

```csharp
// 旧
undoId,   // 不管有没有登记成记录
```

面板见到非空标识就渲染撤销按钮，点下去必然找不到记录。
两处各自看起来都合理，凑在一起就成了「按钮在，但注定失败」。

### 修复

一是执行前把隐式范围解析回参数，让快照有地址可采（`ToolExecutor.Read.cs`）：

```csharp
if (tracking
    && string.Equals(name, "fit_range", StringComparison.Ordinal)
    && string.IsNullOrWhiteSpace(args.Value<string>("range")))
{
    try { args["range"] = UsedRangeAddress(args.Value<string>("sheet")); }
    catch { return ExecuteCore(name, args); }   // 解析失败不改变错误契约
}
```

二是只有确实登记成记录才回传标识，并在没有时说明原因
（`Bridge/AgentChannels.cs`）：

```csharp
var canUndo = undoRecord?.CanUndo == true;
undoId = canUndo ? undoId : null,
undoUnavailableReason = canUndo ? null : "这次适配不能撤销：范围太大，保不住…",
```

宁可不给按钮，也不给一个注定失败的按钮：后者会让用户以为改动可以回退。
而缺按钮又不说原因会被当成故障，所以面板把原因并进同一条提示。

### 混合对齐才是常见情形

适配同时改对齐与行列尺寸，因此快照要覆盖这两个维度
（`SnapshotDetail.Alignment | SnapshotDetail.Size`）。

Excel 对范围内属性不统一的情况返回 Null 而非矩阵。真实表格几乎总是这样——
标题居中、正文靠左。此时只能逐格保存对齐；若范围过大到存不下，就不登记撤销，
而不是假装能完整还原。撤销时也必须逐格写回，否则会把原本参差的排版抹平：
用户撤销的是「适配」，不该顺带丢掉自己排的版。

### 用户侧还需要做什么

Excel 里加载的是安装目录中的 DLL，而当时安装的是 8 月 24 日的构建，
不含上述修复。修复已随本次改动重新安装，重启 Excel 后生效。

## 二、任务进行中可继续输入，自动排队执行

### 原来的行为

处理中输入框被禁用（`composer.disabled = value`）。想到的下一步只能干等，
或者记在别处。而加载项同一时刻只跑一轮，这个限制本身是必要的——
两轮交替写同一个工作簿会互相踩踏。

### 现在的行为

输入框不再禁用。处理中提交的内容进队列，上一轮结束后自动接着跑。

队列放在面板侧而不是加载项：排队中的条目要能看见、能取消，这两件都是界面的事；
后端多一个队列反而要再开查询与撤单两条通道。代价是刷新面板会丢掉未发出的排队项，
但那与丢掉输入框里的草稿是同一量级的事。

排队的消息立即上屏，用虚线气泡与已发出的区分，并显示位次（「下一个」「第 2 位」），
每条带取消按钮。取消不删气泡：那段文字是用户写的，删了就只能重新想一遍，
因此保留原文并标为「已取消，未发送」，需要时可复制回输入框。

### 发送按钮的三种含义

同一个按钮，按当前状态分派：

| 状态 | 含义 | 图形 |
| --- | --- | --- |
| 空闲 | 发送 | 箭头 |
| 处理中 + 有输入 | 加入队列 | 箭头 |
| 处理中 + 输入为空 | 停止 | 旋转圆环，悬停变方块 |

有输入时让「加入队列」压过「停止」：输入框里有字说明用户正打算安排下一步，
此时点按钮几乎不可能是想中断；而要停止只需清空输入框，代价很小——
反过来把排队藏起来则没有同样便宜的替代入口。

图形跟着含义换，不只改 `title`：用户是照着图标点的，画着方块却把消息排进队列
会让人以为点错了。

### 停止会连带清空队列

点停止的意思是「别再往下做了」。若停完当前一轮又自动开跑下一条排队输入，
那就等于没停。被取消的条目仍留在对话流里并标明未发送。

新会话（清空按钮）同理：对话流马上要被清空，排队条目的气泡会一起消失，
留着它们就会在新会话里悄悄开跑，而用户已看不到任何痕迹。

### 单实例轮转

`pumpQueue` 用 `pumping` 作闸门，多个入口同时触发时也只有一条链在跑。
否则两条链会各自取出条目并发调用 `chat.send`，而加载项只接受一轮，
第二条会撞上 `BUSY` 而白丢一次输入。

附件在入队时就取快照，之后加的附件属于下一条——输入框清空后，
「这些附件属于哪条消息」必须已经定下来。

## 三、思考档位界面文案改用英文原名

`Off`、`Minimal`、`Low`、`Medium`、`High`、`XHigh`、`Max`，与三家协议的参数取值
逐字一致（`reasoning_effort`、`output_config.effort`、`thinking_level`）。

原先显示中文（「低」「超高」「最大」）。但档位名同时也是排查时要在日志、请求体和
官方文档之间来回对照的东西，多一层翻译就多一次心算——「超高」对应 `xhigh`
还是 `max`，并不能从字面看出来。

说明文字仍用中文：那是解释用途，不是标识符。原先兜底表是「ID → 中文」的翻译，
现在标签与 ID 同形，兜底表只保留说明文案，缺了选项清单也不会显示错。

## 验证

新增两个验证脚本，均跑真实 Excel。

`scripts\verify-fit-undo.ps1`：造一片标题居中、正文靠左顶对齐的数据（混合对齐是
关键，走的是逐格快照那条路），点真实的「适配」浮层选项，然后点撤销与恢复。
断言不止「声称成功」，还读回单元格确认对齐与列宽真的变了回去、标题原本的居中
没被抹平，并断言日志里不再出现 `NOT_FOUND`。

```text
提示：文字=已适配 1-6 行 × A-D 列：水平居中、垂直居中，并调整了行高列宽。 | 撤销入口=撤销
通过  撤销没有报「找不到该操作记录」
通过  撤销还原了正文原本的靠左与顶对齐
通过  撤销保住了标题原本的居中，没被抹平
通过  恢复重新应用了适配后的列宽
=== 适配撤销验证全部通过 ===
```

`scripts\verify-chat-queue.ps1`：mock 新增 `slow` 场景，慢慢回话并把收到的输入
原样念回来——这样「谁先发出去」不靠时序猜测，而是从回复内容直接读出来。
一轮停在处理中时再投两条，断言进队列而非丢弃或撞上 `BUSY`，然后等队列自动排空
并核对顺序，最后验证取消与停止清空队列。

```text
状态：排队=2 | … | 位次=排队中 · 下一个，排队中 · 第 2 位 | 排队内容=第二条，第三条
通过  上一轮结束后队列自动跑完，无需再次点击
通过  排队期间没有撞上 BUSY
通过  停止后队列已清空，不会接着跑下一条
通过  内部队列长度与排队气泡数始终一致
=== 排队验证全部通过 ===
```

排队状态一律从 DOM 读，不问脚本内部的队列变量：用户看到的就是 DOM，二者若不一致
本身就是缺陷，不该被测试掩盖。面板每轮结束还把内部队列长度写进布局日志，
两处可交叉对账。

### 面板单元测试

- **轮转闸门**：逐条放行每一轮，并在每步取样在途的 `chat.send` 条数，

- **附件归属**：占住一轮后粘甲图入队，再粘乙图入队，放行后断言第一条带的

| 附件改为发送时现取 | 4 项，第一条带错图、第二条没图 |
