# 2026-09-09：点「测试」先问测到什么程度为止

模型列头的「测试」不再直接把整份目录扫完。点下去先给出三档：找到 1 个能用的就停、
找到 2 个能用的就停、全部测试。带目标那两档在累计探出指定个数的**可用**模型后
停止派发新请求。

## 为什么改

一个模型一条计费请求，网关动辄返回几十个 ID，于是一次点击就是几十条请求、要等好一阵。
而用户真正想知道的往往只是「有没有一两个能用的」。

此前没有比它更省的选择：另一个按钮「确认」的作用范围是名单，而名单为空时正是最需要
找模型的时刻。唯一的办法是点下去、看着它跑几十个、中途自己按停止——停止一直有，
但那要求人守在旁边盯着列表变色。

## 提前停不用取消，只停派发

最省事的实现是达标就 `Cancel` 整批。它会同时踩三件事：

1. **丢掉已付费的判定。** `SendAsync` 在 token 已取消时原样上抛 `OperationCanceledException`，
   而 `ProbeManyAsync` 的任务体只 `catch (ProviderException)`。达标那一刻在飞的那几个
   既不会走 `onResult`、也不会被 `ModelAvailability.Record`——请求发了、钱付了、
   判定没了，那几行永远停在灰色且再也收不到 `settled`。
2. **在请求仍在飞时放开单飞闸门。** `Gate` 在 `finally` 里放开。提前返回等于让用户随手
   点的「试一下」与批内剩下的请求并发，而「整批占一次闸门」这个分层设计存在的全部理由
   就是挡住这件事。
3. **孤儿任务。** 异常带着离开 `using (slots)`，`slots.Dispose()` 在已派发任务还在跑时
   执行，它们 `finally` 里的 `Release` 撞 `ObjectDisposedException`，而没人 await 它们。

改成只停派发：`foreach` 里 `break`，`await Task.WhenAll(tasks)` 与 `Gate.Release()`
的结构一字不动。于是 `OperationCanceledException` 仍然专属用户取消，两种结局在类型层面
就分开了，不必靠影子标志去猜。

变异验证：把达标改回 `cts.Cancel()`，「已经发出去的都拿到了判定」变成 1 条判定 / 5 条请求，
「结局报达标」也红——后者因为取消路径上函数是抛出而不是返回的，结局结构体拿不到值。

## 达标检查必须在拿到槽位之后

初版写的是「`foreach` 顶部先看达标、再 `await slots.WaitAsync`」。走一遍并发 5、目标 1、
目录 20：

前五个各自检查（都未达标）、拿槽位、派发；第六轮的检查也未达标（还没有任何结果回来），
然后阻塞在 `WaitAsync`。此时第一个模型回 `Available`，计数变 1，`finally` 才 `Release`。
循环从 `WaitAsync` 醒来时那次检查**已经过去**，照样派发第六个。

于是上界是并发数 + 1，而按钮上写的是「最少 5 条」。实测确认：检查在等槽位之前实发 6 条，
在之后实发 5 条。

这里有个连带的教训：这条断言最初写的上界是 `<= 6`，于是那个变异**照样通过**——断言把它
要防的缺陷容纳进去了。改成写死 `== 5`（连跑三次稳定）之后变异才红。

顺带纠正设计里的一处说法：初版认为置位必须排在 `await onResult` 之前，理由是推送要过
WebView2 桥、期间派发循环会醒。实测这个变异不可观测，因为 `slots.Release()` 在 `finally`
里、必然晚于 `onResult`，循环在整个推送期间一直阻塞着。真正的约束是「置位早于 `Release`」。

## 计数记在通道侧

初版让 `ProbeManyAsync` 返回一个含 `Dispatched` / `Completed` 的结构体，理由是「两者的
差额就是发了请求却没拿到判定的那几条」。这个理由自我推翻：那个差额只在取消路径上非零，
而取消路径上函数是抛出而不是返回的，结构体永远拿不到值。照那样落地，用户中止时日志与
回复会说「实发 0 条」而 `confirmed > 0`——比改之前更假。

改为 `attempted` 与 `available` 由 `AgentChannels` 自己用 `Interlocked` 数。`attempted`
记在 `onStart` 里（拿到槽位之后、发请求之前，这是「这一条真的要计费了」最近的证据）。
结构体只用来带回 `TargetMet`。

## 「可用」只算 Available

目标数计的是 `AvailabilityVerdict.Available`，不含 `Unknown`。限流与我方 15 秒截止时间都
落 `Unknown`，把它们算进去等于在「花了钱没拿到答案」上宣布成功，而且会让运行在一个
「谁也不知道能不能用」的模型上停下来。

`Record` 遇 `Unknown` 直接 return，所以 `confirmed` 会把限流那些也算进去而列表一行都不
上色。因此 `availableFound` 单独推给面板，不让它从 `confirmed` 猜。

## 上界三档相同，下界才是不同的那个数字

规范原有一条 SHALL：整目录确认的控件必须在被用之前说清这一次会发多少条请求。带目标数
以后条数不再是定值。

三档的上界都是整份目录条数（7/7/7 在测试里，实际几十），因为目标可能一个都达不到。
把带目标那两档的上界写成目标数（「最多 2 条」）是这次最容易犯且不报错的一处：用户按那句
话估成本，而账单可能是几十条。变异验证：把上界改成 `scope.target`，三条断言红。

三档靠**下界**与「什么会让它提前结束」区分。并发 5 时带目标那两档至少发 5 条——达标那一刻
在飞的一波收不回来。只写「找到 1 个就停」读起来像 1 条。

并发保持 5 不改：目标 1 若把首波降成 1，前几个模型都不答话时反而更慢，而慢是用户抱怨的
第一件事。省下的量级已经够明显（40 → 5～6）。

## 运行中的分母改成目标数

一次「找到 1 个就停」实际只跑五六个，而分母写目录条数就是「停止 3/40」——读起来是
「还要跑 37 个」，而它随后就停了，看起来像断了。带目标时改成「停止 1/1 可用」，
已测个数移到悬停说明里。

## 三种结局各有各的说法

`stopped` / `target` / `completed` 三取一，用户中止优先。优先级在漏斗窗口里是真会用到的：
达标之后要排空在飞的那几条（每条最长 15 秒），这段时间用户完全能点停止。一旦点了，
在飞任务因取消而 fault，`WhenAll` 抛 `OperationCanceledException`，于是两者同时成立——
必须报「用户中止」，因为只有它意味着有已付费的判定被丢了。

`target` 那一档额外要求实发数小于候选总数，否则「最后一个候选刚好凑够目标」会让界面写出
「剩余 0 个没测」。

最要紧的是第三种：目标没达成而整份目录已测完。那时用户选了省钱的选项却付了全额，
不说出来界面上看不出这件事。变异验证：删掉这一支，断言红。

## 顺带修：迟到的推送会把进度凭空复活

用户中止那条路上，取消从派发循环里抛出，`await Task.WhenAll(tasks)` 根本没执行，在飞任务
无人等待。而收尾的 `finally` 已经推了 `done`，面板收到就把进度清空。之后任何一条迟到的
`settled` 会把进度重新置上，列头按钮回到「停止 n/总」——而后端已无批量在跑，再点它只拿到
`stopped: false`，关面板也不清。

面板因此只在本来就有批量在跑时才由 `settled` 推进进度。判定仍然照落：那些请求已经付过钱。

守卫最初写成「没有批量在跑就整条忽略」，结果把 `starting` 也挡住了，`--picker` 里扫光那一
组当场红了 12 项。会迟到的只有 `settled`——某个模型的 `starting` 是在它自己发请求之前推的，
那时批必然还在跑。收窄之后两边都成立。

## 菜单为什么在流内，不是浮在列表上

外层 `.picker-pop` 是 `overflow: hidden` 且向上弹出，绝对定位的浮层一旦超出它就被静默
裁掉，连滚动条都不留——被裁掉的那一档在界面上没有任何迹象说明它存在。在流内插一行则由
模型列表让出高度（它本来就可滚、且有 80px 下限），装不下时菜单自己滚。

`hidden` 必须显式声明 `display: none`：菜单声明了 `display: flex`，而作者样式里的
`display` 会压过 UA 的 `[hidden] { display: none }`，那时 `hidden` 属性彻底失效而菜单一直
显示着。面板单测只看 `node.hidden` 这个 JS 属性，那时恒绿。变异验证：删掉这条规则，
`--picker` 报「hidden 属性=true 而算出来是 flex」。

菜单下限定在两档（52px）而不是一档：矮视口下一次只露一档时，用户看不出这是个可滚的列表，
读起来像「只有这一个选项」——那与「另外两档被裁掉了」在界面上是同一个样子。
360×340 实测压到 52px 并自己滚，列表守住 80px。

刻意不写 `max-height: min(46vh, calc(100vh - 200px))` 这类算式：矮视口下它会算出 0 甚至
负值，那时菜单在 DOM 里、属性都对、四条边也都不出界，只是高度是零，而按「有没有出界」量
的断言对它全部通过。变异验证：换成那个算式，360×340 下菜单高 23px，断言红。

## 顺带修：对话在飞时说得出原因

后端在对话进行中抛 `BUSY`，而面板的禁用条件不看这件事，`testAllModels` 的 catch 只写宿主
日志。改动之前这是「点一下没反应」，有了菜单就是「走两步仍然只换来一条日志」。
现在 `setBusy` 把这件事告诉选择器，按钮先禁掉并在悬停里说明；后端拒绝时也在列表上方留一句。

## 砍掉的两件事

**按判定重排探测顺序。** 本想把「还没判定」的排到前面，好让目标预算别花在已知能用的模型上。
砍掉的理由：它是一条无规范承载的新外部行为（同一份目录、同一次操作，两次点击的探测顺序
不同），代价之一是扫光不再自上而下走而在列表里跳。而它并不必要——目录顶上那个已知能用的
模型，对「帮我找 1 个能用的」来说停在它身上就是最便宜的正确答案。

**悬停打开菜单。** 会让「点一下」在最常见的鼠标操作下变成「点一下把菜单关掉」。

## 验证

- **`BulkTestTests` 新增四组**：达标后实发恰好等于并发数、已派发的都拿到判定、
  闸门到整批结束才放开、限流不算达标（跑到底）、目标达不到时跑满全程且不谎报、
  目标 0 与负数都全量且 `AvailableFound` 如实计数。判据是**服务端服务了几个连接**——
  回调次数说明不了有没有省钱，而省钱是这个功能的全部理由。
  为此给测试服务加了一个在连接刚开始被服务时就递增的计数：现成的 `Spans` 是在
  `Thread.Sleep` 之后才写的，达标那一刻在飞的几条可能一条都没写进去，而偏小的方向恰好让
  断言更容易假绿。
- **`model-test-all.test.mjs` 60 → 81 条**：原先「点一下就发请求」那一整段改写成
  「开菜单、选一档」——驱动路径变了，不改就是一片红，而放宽断言正是这个仓库付过代价的
  事故。新增菜单三档、上界/下界/提前结束条件、目标数进入 payload、分母是目标数、
  三种结局各自的说法、迟到推送不复活、对话在飞时禁用并说明。
- **`PaneHarness --picker`**：菜单三档都在浮层裁剪框内、各有真实高度、至少露两档、
  装不下时可滚、展开后列表仍有可用高度、列头仍不溢出、两套主题各用自己的背景色。
  跑了 300×560、360×340、420×760、480×760 四种尺寸。
- **变异**：C# 三次（检查位置、去掉检查、改成取消）、面板四次（上界写成目标数、
  分母写回目录条数、去掉迟到守卫、删掉「目标未达成」那一支）、CSS 两次（删 `[hidden]`
  规则、换成会算出 0 的高度算式）。其中两次初次不红，暴露出断言太松与时序太齐，都已收紧。
- **全套**：ToolTests 717、网页 964、`--picker` / `--motion` / `--shake` / `--theme` 全绿，
  `dotnet build -c Release` 0 警告 0 错误。
