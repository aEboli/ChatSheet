## 一、附件：去掉按钮，改为只靠粘贴与拖入

`src/web/index.html`、`src/web/scripts/attachments.js`

删掉了「图片」按钮与它背后的隐藏 `<input type="file">`。粘贴和拖入本就是主要

## 二、文件附件

### 为什么面板侧就把文件读成文本

`readAsText(blob, 'utf-8')` 在面板侧完成解码，传给加载项的是 `{name, text}`。
不传二进制的理由：加载项既不落盘，也没有解析 xlsx/pdf 的能力，能送进模型的
只有文字。让二进制走完整条链路再在最后一步失败，只是把错误推迟。

因此只接受文本类扩展名。二进制格式当场拒绝并给出替代做法，而不是干巴巴的
「不支持」：

| 拖进来的 | 说明 |
| --- | --- |
| xlsx / xls / xlsm | 直接在 Excel 里打开它，我能读你当前打开的工作簿 |
| docx / doc | 可以另存为 txt 或 md 后再拖进来 |
| pdf | 可以复制其中的文字直接粘贴到输入框 |
| zip | 解压后把其中的文本文件拖进来 |

xlsx 那条尤其必要：拖一个工作簿进来是完全合理的期待，而正确做法恰好是这个
加载项的核心能力。

### 分类为什么不能只看 MIME

图片按 MIME 判断（浏览器对图片的判断可靠），其余一律按扩展名走文本路径。
只看 MIME 会错：Windows 把 `.csv` 报成 `application/vnd.ms-excel`，把 `.md`
报成空串。前者会让 CSV 被当成 Excel 二进制拒掉——而 CSV 恰恰是最常拖进来的
那一类。测试里用的就是这个真实值。

### 上限怎么定

`src/ChatSheet.AddIn/Providers/FileSupport.cs`

```csharp
MaxFilesPerTurn = 4;
MaxBytesPerFile = 64 * 1024;    // 64 KiB
MaxTotalBytes   = 128 * 1024;   // 128 KiB
```

依据是上下文预算，不是传输成本。按 `Conversation.EstimateTokens` 的算法
（中文 1.5 字/token），全中文的 64 KiB 约 14,500 token，与一次 5,000 单元格
读取同量级。

合计上限刻意**不等于** 64 KiB × 4：四个满额文件约 58,000 token，已是 200,000
预算的三成，而这些内容一条也压缩不掉——它们在用户消息里，不是
`TrimToBudget` 能压缩的工具结果。取一半，最坏约 29,000 token。

### 为什么拼成文本而不走多模态字段

四种协议都没有「文本文件」这类内容块，各家的文件上传接口又互不相通且要先
上传再引用。拼成带围栏的代码块是所有协议、所有模型都读得懂的形式，也让这份
内容天然进入对话历史，后续轮次仍可引用。

```
附件 1/2：data.csv（1.2 KB）
```csv
名称,数量
铅笔,10
```

按 a.csv 的格式排一下
```

文件在前、提问在后：附件是背景材料，问题是要回答的东西，放最后一句能让它
离生成位置最近。只附文件不写字时补一句「以上是我附带的文件」——否则模型
收到的是一段没有请求的材料，多半会自行猜测意图。

### 围栏长度必须算出来，不能写死三个反引号

Markdown 文件本身就常含 ``` 代码块。用固定三反引号包起来，收尾围栏会提前
出现在文件中间，后半段内容就跑到代码块外面，被当成指令读。`Fence()` 扫出
内容里最长的反引号串再加一，四反引号内容用五个。

内容不以换行结尾时补一个换行，否则收尾围栏贴在最后一行末尾，围栏不成立。

### 系统提示必须同时说两件事

`src/ChatSheet.AddIn/Agent/SystemPrompt.cs`

原有一条「你没有文件系统访问能力」。现在用户能把文件拖进来，只留这一条会让
模型对着眼前已有的内容回答「我读不了文件」。补一条说明：出现「附件 N/M：
文件名」加代码块时，那就是文件的完整内容，可直接使用，不必也无法再去读取。

### 校验为什么两边各做一遍

面板侧校验是为了即时反馈（拖进来就说得出原因）；加载项侧是权威判断——上限值
本就由它下发。`FileSupport.Create` 会重新校验扩展名、NUL 字节与字节数，
`ParseFiles` 另外校验数量与合计。单个不合规就整轮拒绝，与图片一致：静默丢弃
会让用户以为文件发出去了，而模型的回答其实完全没看过它。

NUL 字节判定是内容层面的兜底：扩展名可以被改，内容不会。改名成 `.txt` 的
二进制文件靠这一条识破。BOM 在面板侧去掉，留着会成为正文第一个字符，在 JSON
里直接导致解析失败。

## 三、适配：图标 + 三向横排

按钮从「适配」二字改为四角向外撑开的图标。浮层里三个方向由竖排改横排，
图标在上、名称在下。

横排的理由：三项是同一维度上的方向选择，图标的左右顺序本身就对应左中右，
比竖排更快读懂；浮层也矮一半，不至于盖住上方的对话。

去掉「居中」旁的「默认」标签：当前项已用高亮标出，两套标记同时存在时反而要
多想一步——哪个才是现在生效的。

浮层定位从 `left: 0` 改为 `right: 0`。按钮图标化后位置右移（模型选择器占掉了
左侧余量），`left: 0` 展开的浮层在窄栏里会超出面板右缘被裁掉。

## 四、控件行不再换行（长模型 ID 的实际缺陷）

`src/web/styles/app.css`

```css
.chat-controls { flex-wrap: nowrap; }   /* 原 wrap */
.picker        { flex: 1 1 auto; min-width: 0; }  /* 原 flex: 0 1 auto; max-width: 62% */
.picker-trigger { min-width: 0; }       /* 新增 */
```

`min-width: 0` 是关键。flex 项默认不会小于内容的最小尺寸，不写这一条，长模型
ID 会把选择器顶宽并把整行挤出容器——`nowrap` 就变成了横向溢出。

不换行的前提是有东西可压：除选择器外全是 26px 的定宽图标（`flex: 0 0 auto`），
横向不够时只有选择器收缩，模型名截断成省略号。名字看不全仍可读，比整行错位好。

### 实测：改动前后

用 Edge headless 加载真实面板页，在 iframe 里按各档宽度渲染，把一个 64 字符的
模型 ID 写进选择器后量 `.chat-controls` 的子元素顶边去重数：

| 面板宽度 | 改动前 | 改动后 |
| --- | --- | --- |
| 300px | **4 行**，高 67px | 1 行，高 36px |
| 320px | **4 行**，高 67px | 1 行，高 36px |
| 360px | **4 行**，高 67px | 1 行，高 36px |
| 400px | **4 行**，高 67px | 1 行，高 36px |
| 440px | **3 行**，高 67px | 1 行，高 36px |
| 480px | **3 行**，高 67px | 1 行，高 36px |

改动后各档均为 1 行、无横向溢出、模型名确实是截断（`scrollWidth > clientWidth`
为真而触发按钮本身不溢出）、适配浮层不越界。省下的 31px 归还给输入框。

> 「改动前」是按工作树状态重构的：`git archive HEAD` 取出的是更早的版本，
> 其 `.chat-controls` 尚无 `flex-wrap`，量不到这个缺陷。重构方式是把三处改回
> 原样（`flex-wrap: wrap`、选择器 `max-width: 62%` 不伸缩、三个图标按钮换回
> 文字按钮）。

`app.js` 的布局自检随之改口径：行数超过 1 现在直接标注「应为 1 行，布局缺陷」。
原注释写的是「窄栏挤不下时允许换行，换行本身不算坏」，与新行为矛盾。

## 五、发送与停止合成一个按钮

`src/web/index.html`、`src/web/scripts/chat.js`

删掉独立的停止按钮。同一个按钮三层图形按状态显示其中一层：

| 状态 | 图形 | 点击 |
| --- | --- | --- |
| 空闲 | ↑ 箭头 | 发送 |
| 处理中 | 三层圆环旋转 | 停止 |
| 处理中 + 悬停 | ■ 方块 | 停止 |

三层图形都 `position: absolute` 铺满按钮，切换只是换显示哪一层，按钮尺寸不跳动
（实测三态均为 26×26）。

### 忙时不能禁用按钮

`setBusy` 里删掉了 `sendButton.disabled = value`。上一版有独立的停止按钮，所以
忙时禁用发送是合理的；合并之后若照旧禁用，运行中就完全没有中断入口了——
而中断恰恰只在运行中才有意义。这是合并必须配套的改动，漏掉会让停止功能消失。

`initChat` 里显式调一次 `setBusy(false)`：`index.html` 的 `title` 只是脚本就位前
的兜底，真正的文案由 `setBusy` 统一给。两处各写一份的话，改了一处就会不一致。

### 三层圆环为什么各不相同

每层给不同的弧长、速度与方向（1.1s 正向 / 0.85s 反向 / 0.6s 正向）。三个同步的
同心弧看着像一个静止的图案在整体旋转，说明不了「还在动」。

`transform-origin: 8px 8px` 必须显式给：SVG 元素默认绕自身包围盒左上角旋转。

`prefers-reduced-motion` 下动画被全局关掉，圆环会停在三段短弧上，看着像图标画
坏了。因此在该媒体查询里把 `stroke-dasharray` 去掉，补成三个完整同心圆。

## 六、扫帚图标与悬停说明

「新会话」改为扫帚图标。控件行现在除模型选择器外全是图标，没有文字标签，
悬停说明成了它们唯一的自解释途径，因此每一个都带 `title`：

| 控件 | 悬停说明 |
| --- | --- |
| 模型选择器 | 模型、思考等级、是否会降级（脚本填） |
| 清（扫帚） | 清空当前会话，重新开始 |
| 适配 | 适配当前表：选水平对齐，垂直固定居中，并自动调整行高列宽 |
| 三个方向 | 靠左/居中/靠右对齐并适配行高列宽 |
| 审批 | 当前策略、说明、点击切换（脚本填，另给写死的兜底值） |
| 上下文圆环 | 占用量、阈值、可点击压缩（脚本填） |
| 发送 | 空闲「发送（Enter）」，忙时「正在处理，点击停止」 |

用原生 `title` 而非自绘浮层：控件行在面板底部，上方已有两个向上弹出的浮层
（模型选择器、适配），自绘 tooltip 会与它们叠在一起。原生 title 由系统绘制，
浮在一切之上且不参与布局。

审批图标的 `title` 由脚本按设置填，在设置返回前是空的，因此 HTML 里另给一个
兜底值——脚本没跑完时悬停也该有话可说。

## 已知边界

- **文件内容不可压缩。** 它在用户消息里，`TrimToBudget` 只压缩工具结果、
  只丢弃早期消息。附了满额文件的那一轮，这 29,000 token 会一直占着，直到该
  消息本身被作为「早期记录」整条移除。合计上限取预算的一小部分正是因为这个。
- **非 UTF-8 编码的文件会出现替换字符。** `readAsText` 固定按 UTF-8 解码，
  GBK 编码的 CSV（Excel 在中文 Windows 上的默认导出编码）会解出乱码。NUL 检查
  拦不住它——替换字符 U+FFFD 不是 NUL。用户看到的是文件条正常显示、模型收到
  乱码。要解决需要编码嗅探，属于独立改动。
- **拖入 Excel 里的单元格区域不会触发附件。** Excel 内部拖拽给的是
  `text/html` 与私有格式，不是 `Files`，因此 `dragover` 的 `types.includes('Files')`
  为假，整段逻辑不介入。这是对的——表格数据应该用工具读，不是当附件传。
- **悬停停止有约 0.5 秒的鼠标停留成本。** 原生 title 的延迟不影响点击（方块
  是 `:hover` 立即换的），但用户若不悬停就不知道那里能停止。欢迎语里写了这一点。
