# 2026-08-26：按模型能力回退

不支持原生工具调用的模型改用文本指令协议，照样能读写工作簿；连指令块也写不对的
退为顾问模式。没有视觉能力的模型，配了中转模型就先把图转成文字，没配就去掉图片
继续这一轮并明确告知。

## 问题

加载项对每个模型都发同一种请求：一律附带 17 个工具的函数声明（约 2100 token），
图片一律塞进多模态字段。这等于假定「所有模型都能调用工具、都能看图」。

不具备工具能力的模型有两种表现，都不好收场：

- 服务端以 400 拒绝带 `tools` 的请求。整轮直接失败，用户只看到一条接口错误，
  而真正的原因是「这个模型不能这么用」。
- 服务端接受但模型不会用。它对着 2100 token 的工具声明，回一句「我无法访问你的
  表格」。`SystemPrompt.cs` 的注释里早就记下了这个实测现象（DeepSeek-V4-Flash），
  当时的处置是把「你已经连上工作簿」写到系统提示最前面——那是在跟症状周旋：
  声明发过去了，模型就是不发工具调用。

视觉那侧更直接：`ImageSupport.ProtocolSupportsImages` 直接 `return true`，注释写着
「具体模型可能不支持——那只能等服务端报错」。于是用户贴一张截图，得到的是一条原始
400。更糟的是有的服务端不报错、静默忽略图片，模型就对着不存在的内容作答。

共同的根子：加载项没有「这个模型能做什么」这个概念，因此既无法回退，也无法告知。

## 改动

按「连接 + 模型」建能力档案，两条回退链各自成立。档案只在本次面板会话内有效，
不落盘——网关随时可能补上支持，而落盘的判定要用户自己去清理才能翻案。

### 工具：原生 → 文本协议 → 顾问

**文本协议**不发 `tools` 字段，把工具清单写进系统提示，约定模型用围栏块发起调用：

````text
```chatsheet:tool
{"tool": "write_values", "args": {"range": "A1:B1", "values": [["名称", "数量"]]}}
```
````

清单用紧凑签名而不是完整 JSON Schema：

```text
- `write_values(range, values, sheet?)`（写操作，可能需要用户批准）：向范围写入字面值。
```

弱模型读不动嵌套 schema，而紧凑签名把「必填/可选」直接标在参数名上，比 `required`
数组更容易照着写对。体积也只有原生声明的三分之一（测试里断言了这一点）。

解析出的调用走**与原生调用完全相同的链路**：同一套审批、同一套参数校验、同一套
上限、同一条撤销记录、同一张操作卡片。文本协议不提供任何原生调用拿不到的东西，
也绕不过任何检查——这是它敢自动启用的前提。

**顾问模式**在文本协议也走不通时启用：不带工具，系统提示改写为「你不能读取或修改
用户的工作簿」。这一条是为了防最坏情况——模型既不会调用工具，又被提示反复告知
「你已经连上工作簿、有读写权限」，于是编造出「我已经帮你填好了」。

进入文本协议的两条路：

| 触发 | 判据 |
| --- | --- |
| 服务端明确拒绝 | 4xx 且错误文本提到 `tools`、`tool_choice`、`function calling` 等协议字段名 |
| 模型收下却推辞 | 原生模式下零调用，且正文同时出现「做不到」与「表格」两层意思 |

第二条是启发式，因此加了三道闸：只在自动探测下生效、每个连接+模型只试一次、
必须同时命中两层意思。只认「碰不到工作簿」这一类说法而不认泛泛的「我不能」——
模型拒绝越权请求时也会说「我不能」，那是对的，不该触发降级。

### 视觉：中转 → 去图

服务端因图片拒绝时记下该模型没有视觉能力，然后：

- **配了视觉中转模型**：每张图单独发给它，沿用同一套连接与密钥、只换模型名。
  提示词限定在表格用途上（结构、表头、数值、报错原文），因为泛泛地「描述这张图」
  只会得到「一张电子表格的截图」这种无用回答。描述以文本替换原图进入上下文，
  并注明是转写、涉及数值要读表核对——不注明的话模型会把有损的描述当事实写进单元格。
- **没配**：去掉图片重发，并告知模型「用户附了图但你看不到，不要假装看过」。

描述按图缓存：一轮可能跑几十步，每步重新转述同一张图既慢又多花钱。

两条路都必须在上下文里留痕。静默丢图是这条链路最危险的失败方式——用户以为模型看过
自己的截图，于是会相信一个从未基于它的回答。

### 手动指定

设置页「高级参数」里新增两项：工具调用方式（自动探测/原生/文本指令/不用工具）与
视觉中转模型。手动指定的意义在于服务端**不报错**的那些情形：静默忽略工具或图片时
探测无从触发，而遇到这种网关的用户本就在找开关。改动这个选项会作废已探测的结果，
否则从「文本指令」改回「自动探测」等于这个选项没生效。

## 三处容易忽略的细节

**指令块不能进对话气泡。** 正文是逐字推给面板的，等整段收完再清理就晚了——JSON 的
头几个字已经渲染出去。因此流式输出经过一道闸门：看到行首围栏就先攥住不外放，等到能
判定时再决定整块吞掉还是原样放行。普通代码块只会因此晚一帧显示，不会显示错。

闸门还得处理两种边界：围栏的三个反引号会被拆到不同的增量里（末尾疑似半个围栏时要
留着），以及流断在块中间（攥着不放会让这段文字凭空消失，因此 `Flush` 必须定性）。

**能力判据必须排在截断判定之后。** 被长度上限截断的一步既没有工具调用也没有指令块，
形态与「不会用工具」一模一样。顺序反了的话，把输出上限设小一点就会被判成模型不支持
工具。

**文本协议下的工具结果要标记出身份。** 协议里没有 `tool_call_id` 可用，结果只能作为
`user` 消息回灌，于是上下文压缩认不出它是工具结果——而工具结果恰是体积最大、最该
优先压缩的那一类。丢了这个标记，压缩会转去丢弃真正的对话历史。

## 验证

- `ChatSheet.ToolTests.exe`（真实 Excel）：通过 427，失败 0（新增 57 项）。
  其中一半是反例——401、503、图片类错误都不能被判成「不支持工具」，
  正常作答与合理拒绝都不能被判成推辞。判据认宽了会白白降级，认窄了则整轮失败
- 面板单测 18 个文件合计 453 项通过，失败 0（新增 13 项）
- 端到端（真实 Excel + mock）：
  - `-Scenario notool`：首个请求带 17 个工具被 400 拒绝 → 降级为 Text →
    指令块被解析成 `write_values` → **A1=名称 B1=数量 真的写进了单元格** →
    本轮正常收尾。带 tools 的请求只发了 1 次，说明降级对后续步骤生效
  - `-Scenario novision -WithImage`：图片被拒 → 去图重发 → 模型收到「有图但你
    看不到」的说明 → 正常收尾。重发时确实不再带图片
  - `-Scenario novision -WithImage -VisionRelayModel mock-vision`：图片被拒 →
    经 `mock-vision` 转写 1 张 → 描述注入上下文 → 主模型据此作答
- 设置页布局：控件 9 个（原 7 个），200px 与 455px 两种宽度下均无横向溢出。
  两个新控件只用 `.input` / `.field-hint` 等既有类，其颜色全部走调色板变量，
  因此两套主题自动适配
- Release 构建 0 警告 0 错误
- 变异验证：把闸门改成「识别为指令块也放行原文」，`闸门吞掉指令块` 与
  `逐字喂也能吞掉指令块` 两条如期失败；把 `vision-fallback` 改成不落通知，
  面板侧 5 条如期失败。确认断言不是对着空节点通过
