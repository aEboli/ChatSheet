# 2026-08-31：面板点了没反应时说清原因和该怎么办

点功能区的「ChatSheet 面板」而面板没出来时，现在会弹一个原生对话框，
一句话说清成因、给出一个能做的动作，并带上日志路径。同时把三条「点了没反应」
的成因就地修掉了——它们本来只写日志，或者连日志都不写。

## 问题

`0.6.0` 里点面板没反应有十一条路径，全部对用户静默。加载项里一处 `MessageBox`
都没有，面板自身是唯一的输出通道——而它恰好就是坏掉的那个东西。

真实发生过的一次（`%LOCALAPPDATA%\ChatSheet\logs\addin-EXCEL.log`）：

| 时刻 | 日志 | 实际情况 |
| --- | --- | --- |
| 10:57:41 | 侧边栏创建成功 | 面板正常 |
| 11:26:28 | 焦点守卫已卸载 | Excel 把面板控件销毁了，加载项没察觉 |
| 11:28:58 起 | 设置侧边栏可见性失败 `0x800A01A8` | 每次点击都在戳一个已经拆掉的对象 |

`EnsurePane` 只看 `_pane != null` 就早退，而没有任何地方会在宿主销毁窗格后把它
置空——`_pane` 全仓只有三处赋值，最后一处在 `OnDisconnection` 里，那是关闭流程。
于是这个 Excel 会话此后再也开不出面板，只能重启。

## 只读工作簿不是成因

这一条值得单独写，因为它正是本次的报障方向，而它是个误导。

只读工作簿是 `Workbooks` 的正常成员，有真实的 `Window`，面板照常能开；
`Workbook.ReadOnly` 只是个状态标志，官方文档没有任何一处把窗格创建条件挂在它上面。
真正拦住面板的是**没有可停靠的文档窗口**，判据是 `Windows.Count == 0`。

两者容易混为一谈，是因为「受保护的视图」恰好同时是只读的：受保护的视图里的工作簿
**不属于** `Workbooks`，也不贡献 `Window`，所以 `Windows.Count` 是 0、
`ActiveWindow` 是 `Nothing`，窗格没有能挂的地方。它落在
`Application.ProtectedViewWindows` 里，这也是判定它的正路。

所以判定里刻意没有「只读」这个维度。把只读当成因会让用户去改文件属性，
而那件事跟面板打不开毫无关系。`PaneOpenDiagnosisTests` 里有一条用例专门钉住这一点。

## 改动

### 成因判定做成纯逻辑

新增 `src/ChatSheet.AddIn/PaneOpenDiagnosis.cs`：`HostWindowState` 是宿主窗口状态
的快照（文档窗口数、受保护的视图窗口数、探测是否被拒），不持有任何 COM 对象；
`Classify` 按优先级判成六种成因，`Describe` 给文案。这样判定能在没有 Excel 的
环境里直接验证——而「只开着受保护的视图」这类状态手工复现一次相当费事。

优先级是先看宿主有没有窗口，再看加载项自身状态。反过来会把「没开工作簿」
误报成注册问题，让用户白重装一遍。

探测被拒（宿主忙或有模态对话框）时读到的 0 不可信，单独判成「Excel 正忙」，
不能断言「没有工作簿」。但若受保护的视图数读到了，就以它为准。

`Hosts/HostProbe.ReadWindowState` 负责填这个快照。它区分两种读不到：
`Windows.Count` 读失败记成探测被拒；`ProtectedViewWindows` 读失败按 0 处理——
那个集合是 Office 2010 才有的，WPS 表格也未必提供，因此不能据此判成「Excel 正忙」。

### 显示失败要能被发现，且就地重建

`TaskPaneController.IsVisible` 的 setter 原先把异常吞掉。改成 `TrySetVisible`，
设置后**回读确认**再返回成败：宿主拒绝显示有两种表现，抛异常和「调用成功但窗格
没出来」，后者在日志里与正常打开一模一样，只看异常会把它当成功放过去。

`ApplyPaneVisibility` 在显示失败时判定窗格已失效，`DisposePane` 后重建并重试一次。
代价是本次会话的对话内容重新开始，但这好过面板此后再也打不开。

隐藏失败不弹窗也不重建：用户要的是面板消失，而它确实不在眼前。

### 功能区按下态不再盲信

用户用面板自己的关闭按钮关掉面板时，宿主不通知加载项，功能区仍按「按下」记着。
下一次点击于是送来 `pressed=false`，去隐藏一个已经隐藏的面板——点了没反应。
这是日常最容易撞上的一条，而且日志里连一句警告都没有。

改成目标状态按面板的**实际可见性**取反，读得到就以它为准，读不到才退回 `pressed`。

### 挂在别的工作簿窗口上也算打不开

窗格创建时绑定在当时的活动窗口上，且绑定不可改（`CustomTaskPane.Window` 只读）。
Excel 2013 起每个工作簿有各自的框架窗口，于是「在 A 工作簿开了面板，切到 B
再点按钮」时，窗格仍报告自己可见——它在 A 的窗口里确实可见——但用户眼前什么都没有。

这条路径**不抛异常也不返回失败**，靠错误捕获永远发现不了。
`IsParentedToActiveWindow` 比对窗格父窗口与当前活动窗口的 `Hwnd`，
确凿不一致才重建；读不到句柄就按「没问题」处理。

**先用 COM 标识比对，翻车了。** `Marshal.GetIUnknownForObject` 对 Office 对象不是
有效的标识：Excel 每次读 `ActiveWindow` 都交回一个新的代理，指针每次都不同，
于是同一个窗口也被判成不同。实测四次点击建了四个面板、六次误判，
而重建会把这一轮的对话内容一起丢掉——比它想修的缺陷严重得多。
换成 `Hwnd` 后同一场景是四次点击、零次重建。

也不比 `Caption`：同名工作簿会误判。当初避开 `Hwnd` 是担心宿主兼容性，
但本项目只做 Excel（WPS 个人版加载不了第三方加载项），这个顾虑不成立。

### 文案

六种成因各一句，形状沿用面板内兜底文案那一套：一句话说清发生了什么 →
括号里补最常见的触发条件 → 最后一句交代还能做什么。不逐一枚举内部失败步骤。

| 成因 | 给用户的动作 |
| --- | --- |
| 受保护的视图 | 点黄色提示条里的「启用编辑」，再点面板 |
| 没有文档窗口 | 先新建或打开一个工作簿 |
| 宿主忙 | 关掉表格上的对话框、等当前操作结束 |
| 建立面板的接口没送达 | 完全退出 Excel 重开；仍不行就重跑 `install.bat` |
| 面板控件创建失败 | 重跑 `install.bat`，然后完全退出 Excel 再打开 |
| 显示被拒且重建无效 | 完全退出 Excel 重开；每次都这样就带日志反馈 |

文案里不出现「窗格」「CreateCTP」「COM」这类只对开发者有意义的词，有单测钉住。
「诊断」按钮也不能作为补救措施——它走的是同一条 `ShowPaneRoute`，面板打不开时
它同样打不开。

## 两处容易踩的坑

**自动化入口不能弹框。** `ShowPaneRoute` 同时是自动化接口的入口
（`AddInAutomation.ShowPane` ← `scripts/verify-panel.ps1`，跨进程 COM 调进 STA）。
那条路上弹模态框会让 PowerShell 的调用永不返回，验证脚本从「报错退出」变成
「挂住不动」——而那正是最需要跑验证的机器。因此加了 `interactive` 参数，
功能区三个回调传 `true`，`ShowPaneForAutomation` 传 `false`。

**模态框会被重入。** `MessageBox.Show` 起一个嵌套消息循环，期间宿主继续派发消息，
用户可以再点一次按钮把第二个框叠上来。`_promptShowing` 挡住重入。
对话框的所有者取宿主主窗口（`Application.Hwnd`），否则它可能跑到 Excel 后面去，
那会表现为 Excel 整个卡住。

## 验证

### 单元：成因判定

`tests/ChatSheet.ToolTests/PaneOpenDiagnosisTests.cs` 27 条：窗口状态优先于加载项
状态、只读不构成成因、受保护的视图与普通工作簿并存时不误判、探测被拒的两种处理、
六种成因都有文案且都带动作、文案不含内部术语、日志路径缺失时退回环境变量写法。
全套 569 条通过。

变异一次确认断言真的在验：把受保护的视图那条判定短路掉，2 条用例当场变红。
（这一步是必须的——面板类的断言很容易对着空值全绿。）
其中「文案不含内部术语」当场抓出一处真问题：`FactoryMissing` 原文写的是
「没有把窗格接口交给本加载项」，含日志专用词「窗格」。

### 端到端：真实功能区点击

`scripts/verify-pane-open.ps1` 22 项全过，全程 UI 自动化点真实按钮：

| 检查 | 结果 |
| --- | --- |
| 只读工作簿上面板能打开、不判成因、不弹提示 | 通过（视口 469 CSS 像素） |
| 连续开关四次不重建面板、不误判跨窗口 | 通过（创建 0 次，误判 0 次） |
| SDI：第二个工作簿窗口里点按钮，识别跨窗口并重建 | 通过 |
| 制造真实失败后弹出提示，标题/成因/动作/日志路径俱全 | 通过（第 800 毫秒抓到） |
| 还原注册后面板恢复正常、不再弹提示 | 通过 |

**不能用自动化接口验提示**：那条路刻意传 `interactive=false`，永远不弹框。
只有真实点击才走到弹框分支，所以验证必须走 UI 自动化。

制造真实失败的手法是暂时把 `ChatSheet.TaskPane` 的 ProgID → CLSID 映射指向空 GUID，
`CreateCTP` 在调用时刻解析 ProgID，因此必然失败。脚本在 `finally` 里还原并复验。
另有两条路试过但造不出失败，记在脚本注释里以免重走：删 CLSID 下的 `Control`
子键（Excel 照样建出了窗格）、把 `InprocServer32` 的 `Class` 改成不存在的类型
（该键下还有按程序集版本分的子键，各自带着正确类名，mscoree 从版本子键解析）。

### 环境上踩的三个坑

都与产品无关，但下次验证会再遇上，记在 `scripts/verify-pane-open.ps1` 的注释里：

- **提权环境下 `GetActiveObject` 附加不上 Excel**，报 `MK_E_UNAVAILABLE`
  ——提权的 Office 不在 ROT 里登记。改用 UI 自动化，不用 COM 附加。
- **屏幕 150% 缩放**。进程不声明 DPI 感知时看到的桌面只有 1707 宽，
  而 UIA 报的是物理像素，截图和点击会整体偏移到别处。
- **抓模态框不能用 UIA**。Excel 主线程卡在模态框的嵌套消息循环里，
  对该进程窗口的 UIA 属性读取会超时抛异常，被 `try/catch` 一吞就等于没看见
  ——曾 200 次轮询全空，而日志证明框一直开着。改用 Win32 `EnumWindows`。

### 仍未端到端验证的一条

**「用面板自己的关闭按钮关掉，再点一次功能区」没有在真实 Excel 里走通。**
那个 X 不在 UIA 树里（Excel 画在 `MsoCommandBar` 内，不暴露子元素），
`WindowPattern.Close()` 又只隐藏窗口、不把 `Visible` 置为 false，
复现不出「宿主已隐藏而功能区仍记着按下」这个前提；按坐标点也没命中。

该路径的逻辑成立且相邻行为已验证：连续开关四次证明 `TryGetVisible` 读得准，
SDI 那一项的日志里能看到 `pressed=False` 被改判为「打开」，
即「不盲信 pressed」这条分支确实在工作。但「X 关掉之后一次点开」这个具体组合
仍只是逻辑上成立。

## 顺带发现、但这次没修的一个真缺陷

**面板视口退化时，宽度校准会把面板放大到半个屏幕并落盘。**

复现：Excel 窗口处于最小化状态时点开面板。此时面板拿到的视口只有 69 CSS 像素，
`AdjustWidthForCss` 据此算出「要补 331 CSS 像素 × 1.5 缩放」，
把宿主宽度从 719 拉到 1217（屏幕一半的上限），并写进 `settings.json`。
之后每次打开面板都是这个宽度。

这是既有逻辑的缺陷，与本次改动无关：校准没有对「视口小到不可能是真实布局」
设下限。修法应当是视口低于某个阈值时直接不校准，等布局稳定后再算。
本次只记录，没改——它属于宽度那条线，不属于「点了没反应」。

（开发期间我自己触发过一次，把用户的 `paneWidth` 从 719 改成了 1217，已改回。）

## 没动的东西

以下几条也是「点了没反应／面板不对」，但成因与本次无关，刻意没碰：

- WebView2 初始化失败——面板会出来并显示兜底文案，本来就不静默
- 导航失败导致面板空白——`ShowWebView` 无条件隐掉兜底标签，没有订阅
  `NavigationCompleted`，日志还写着成功。这是独立缺陷
- `ResolveControl` 取不到托管控件时，日志先报错又紧跟一句「侧边栏创建成功」
- `OnGetPanePressed` 在窗格挂在别的窗口上时仍报告「按下」。它被宿主高频调用，
  不适合每次都做 COM 往返比对父窗口；点击路径上已经处理了这种状态
- 受保护的视图下功能区没有自定义选项卡，因此那条文案实际很难被看到。
  留着是因为「受保护的视图 + 另开着普通工作簿」时仍可能走到判定，
  且判定本身要能把它与「没有工作簿」区分开
