# 提案：常用模型名单与真实对话中学到的可用性

## 问题

模型选择器把 `GET /models` 返回的 ID 原样列出来。网关动辄返回几十上百个，其中能用的
往往只有两三个：有的没有配额，有的账号无权限，有的只是别名，有的一发就 404。
用户要确认哪个能用，唯一的办法是选中它、发一句话、看报什么错——错了再换下一个。

问题的根子在于协议本身不提供答案。`CapabilitySignals.cs:5-11` 已经记下这件事：
没有任何协议提供「该模型支持什么」的查询接口，`GET /models` 只给名字。
`ChatClient.cs:322` 的 `ExtractModelIds` 把 `owned_by`、上下文长度这些字段全部丢弃，
不是疏漏——那些字段各家给法不一，也都不回答「我能不能用」。

于是「不可用」目前只有一个信号来源：真实对话失败后的启发式（`CapabilitySignals.cs`）。
它是被动的、事后的，而且结论随进程消失。用户上一次踩过的坑，下一次重开 Excel
还要再踩一遍。

需要区分两件被混在一起的事：

- **「我常用哪几个」** 是用户的选择。它稳定、跨会话成立，用户自己最清楚。
- **「这个模型现在能不能用」** 是外部事实。它会变（配额按日月重置、网关随时调整）。

把这两件事合成一张「可用模型表」会同时做错两头：用户的选择被判定结果覆盖，
判定的误判又变成永久的隐藏。

## 改动

### 「可用」的口径

只指一件事：**一次请求到达了这个模型并得到回复**。

刻意不把「支持工具调用」和「支持视觉」算进来。既有规范
（`openspec/specs/model-capability-fallback/spec.md:148-158`）已经明确：模型连指令块
都写不对时仍然继续服务，改为给出公式与操作步骤。也就是说**不支持工具的模型是可用的**。
把它算成不可用，会把一个规范认定可用的选项从用户眼前拿掉。

工具与视觉的能力判定继续留在既有的能力档案里，与本能力互不改写。规范已要求这两条链
互斥（同文件 `:176-177`），可用性是第三个维度，同样不与它们合流。

### 判定只从真实对话里来

本期不发任何额外请求。信号取自用户已经付过钱的那一轮：

- **可用**：本轮收到过任何流式事件。到达了模型就是可用性的全部主张，之后无论
  出什么错都不改这个结论。落点在 `AgentRunner.StreamStepAsync` 的事件回调里——
  不用 `ChatClient` 的 `delivered`，那是重试循环内的局部变量（`ChatClient.cs:102`），
  只说明「这一次尝试」交付过。
- **不可用**：本轮失败，且服务端原始错误点名了这个模型
  （`model_not_found`、`does not exist`、`no access to` 这类）。
- **未知**：其余一切。密钥被拒、限流、5xx、超时、网络故障、我方请求有问题，
  说的都是账号或网络，与模型无关。也是任何拿不准情形的归宿。
- **从未发过一轮的模型没有判定**，显示为「未确认」——这正是二期要补的那部分。

零额外请求就能覆盖用户真正用过的每一个模型。

### 判据必须读服务端原文，不能读 `Message`

这是本期唯一的接入层改动，也是判定能不能成立的前提。

`BuildHttpErrorAsync` 把我们自己拼的提示塞进了 `Message`（`ChatClient.cs:412-414`），
而 `HintFor(404)` 返回的是「请检查接口地址与模型名是否正确」——**含「模型名」二字**
（`ChatClient.cs:491-492`）。`ProviderException` 只有 `Code`、`Message`、`RetryAfter`
三个成员（`Protocols.cs:210-225`），没有保留未拼装的原文。

照 `CapabilitySignals` 的风格加中文 needle 去认「点名模型」，我们自己的提示就会把
**每一个 404 都喂成假阳性**：地址填错的裸 404 会给名单里每个模型依次判死刑。

因此给 `ProviderException` 增加一个只含服务端原文的 `Detail`，分类只读它。
`Message` 的拼装保持不变——那是给用户和日志看的，两个用途不该共用一个字段。

裸 404 因此判未知：只有原文点名模型才判不可用。这与既有规范
`spec.md` 的「状态码不单独决定」一致。

### 顺路修一个现存缺陷

`LooksLikeVisionUnsupported` 匹配裸子串 `"image"`（`CapabilitySignals.cs:96`）。
选一个名字里带 `image` 的模型（`gpt-image-1`）、附一张图、发送：那句
`model 'gpt-image-1' does not exist` 是 4xx 且含 `image`，于是被记成「不支持图片输入」，
白花一次视觉中转请求去描述图片、剥掉所有图、再用同一个不存在的模型重试一遍，
最后告诉用户「当前模型没有视觉能力」（`AgentRunner.cs:472-482`、`:724-790`）。

这个缺陷今天就在。新增的可用性标记会把同一条错误正确读成「不可用」，于是同一行上
出现两个互相矛盾的标记——是新标记把它照出来，不是新标记造成的。

补上镜像判据：**错误点名了模型时，它不是任何能力信号**。既有代码已经有反方向的
同类守卫（`CapabilitySignals.cs:60-65` 让工具判据先排除视觉错误），这是第三条。
这是本期对 `CapabilitySignals` 的唯一改动。

### 常用名单（落盘）

每个模型一个开关，按连接记住。名单是用户意图，落盘。

名单另存一个文件而不进 `settings.json`：后者的 `Save` 按白名单整体重建文档
（`Settings.cs:289-307`），任何只读不写的键会被下一次任意写入方抹掉；而名单的归属
是连接，不是设置。

原子写用 `File.Replace` 而**不**照抄 `Settings.cs:317-321` 的 Delete + Move：
后者在两步之间崩溃会同时失去新旧两份。设置丢了只是回默认值（已有兜底），
名单丢了是用户手工标注的成果没了。`File.Replace` 一次替换并顺带留下备份。

分组文件里「归属不一致」是常态而非错误状态，因此只校验当前连接那一组，
其余组按字节原样保留。这与 `DropModelFromOtherConnection`（`Settings.cs:141-160`）
的处置**不同**——那是为「只存一个模型」写的，直接照搬会在读盘时删掉其他所有连接的分组。

本机 CLI 模式**不做地址戳记**。原设想是把解析出的地址记下来、不符即丢弃，但它
既做不到也不够：`TryReadCodexBaseUrl` 吞掉所有异常返回 null，
「读不出来」与「就是官方地址」分不开（`LocalCliConfig.cs:213-214`、`:232-264`）；
而地址根本读不到——token 缺失时 `ReadClaude` 在算地址之前就抛了（`:166-174`）。
失效交给下面那条展示期阀门，它一次管住全部原因，还不必在名单的读写路径上碰密钥。

本机 CLI 按**解析后**的 CliKind 归组，而不是配置里的 `CliSource`。
`ConnectionKey()` 是 `Mode|CliSource`（`Settings.cs:114-119`），把下拉从「自动」
钉成「Claude」会让键从 `LocalCli|Auto` 变成 `LocalCli|Claude`，而
`LocalCliConfig.Resolve` 返回的凭据一模一样——用户刚弄清自己在用哪个 CLI 就去钉住，
名单原地失联，而且旧分组还在盘上够不着。

手填的模型 ID 自动进名单。落点是 `applyManualModel`（`picker.js:246-252`）——
它本身就是「不在目录里也要可见」的第三处特例，本次要加的是第四处。

### 排序无条件生效

名单里的模型排在目录之前，其余保持后端给的字母序（`ChatClient.cs:368`）。
不需要任何开关，什么都不藏，所以没有把人锁在外面的可能。这也是选择器已有的取向
（`picker.js:210-213`：不支持的思考档位刻意不隐藏，只标注会降级）。

判定到达不改变行序：一个标记忽然出现就让行跳走，比没有标记更难用。

### 一个开关收窄列表

模型列列头一个开关，默认关——老用户升级后选择器逐字不变。

阀门只有一条，但它同时管住空名单与全部失效：**开关开着而名单里没有一个模型出现在
当前目录里时，显示完整目录**。原方案的阀门只覆盖「名单为空」，于是名单非空但全部
失效（换了网关、模型下架、几个月前打错的 ID）时开关一开，选择器只剩当前模型，
能用的全被收起来——正是那条阀门想防的表现。

当前选中的模型永远可见，无论它在不在名单里、开关开没开。

第一次标注不立刻收起其余的。开关开着、名单刚从空变成一项时，浮层继续显示完整目录，
只在列头把「只看名单」明确成下一次点击。否则用户的动作是「记住这个」，
效果却是「藏起另外 59 个」，而浮层里没有任何东西把两者连起来。

开关走 `session.update` 而不是 `settings.save`。picker 唯一的写回通道就是
`session.update`（`picker.js:275-278`），而 `settings.save` 发的是设置页那份 `current`
全量快照（`settings.js:594`），且 `initSettings` 每个面板生命周期只跑一次
（`app.js:48-51` 的 `settingsLoaded` 守卫）。用户在选择器里拨了开关、去设置页点保存，
就会把面板启动时的旧值写回去，开关静默回退。因此这一项**要**加进 `settings.js`
的只读字段删除名单。

### 判定的生命周期

判定按「连接 + 模型」记在内存里、不落盘，理由与能力档案同源：网关随时可能补上配额
或权限，落盘的判定要用户自己去清理才能翻案。

但不说「本次面板会话内有效」——代码做不到这件事。`EnsurePane` 是
`if (_pane != null) return;`（`ComAddIn.cs:225-230`），关闭面板只改 `IsVisible`
（`ComAddIn.cs:186`），控件不销毁、`AgentChannels` 不重建，而档案字典是进程级静态字段
（`ModelCapabilities.cs:69-70`）。既有注释写的「重开面板重探一次」，代码从来没有兑现过。

如实写作用域：**Excel 进程存续期间有效，换连接或写入密钥时作废该连接的判定**。
既然判定只来自真实对话，后一轮的证据总会覆盖前一轮，过期判定的代价比探测时代小得多。
按连接作废需要一个 `ModelCapabilities` 没有的操作——它只有全清的 `Reset()`
（`ModelCapabilities.cs:87-90`）。

### 大小写口径统一

现在三处不一致：`ModelCapabilities` 的字典用 `Ordinal`（`:69-70`）、
`ChatClient.cs:368` 的去重用 `OrdinalIgnoreCase`、`picker.js:250` 的 `includes`
区分大小写。用户手填 `GPT-4O` 而目录里是 `gpt-4o`，判定会落在一个键上、
行渲染查另一个键，界面表现是「转完了，行上什么都没变」。

本期新增的两处（判定缓存、名单）一律忽略大小写，面板侧比较也折叠后再比。
刻意不改 `ModelCapabilities` 的比较器——那是既有能力回退的行为，不在本次范围内。

## 影响范围

新增 `Providers/ModelAvailability.cs`（三态、按连接+模型的缓存、错误分类、按连接作废）、
`Storage/FavoriteModels.cs`（名单的落盘与按连接归属）、
面板 `scripts/model-favorites.js`（名单与三态的面板侧投影）。

改 `Providers/Protocols.cs`（`ProviderException.Detail`）、
`Providers/ChatClient.cs`（填 `Detail`）、
`Providers/CapabilitySignals.cs`（`IsClientError`/`Mentions` 提为 internal，
新增「点名模型」判据并让两条能力判据先排除它）、
`Agent/AgentRunner.cs`（两处回写）、
`Bridge/AgentChannels.cs`（下发名单与三态、名单读写、开关、按连接作废）、
`Storage/Settings.cs`（开关一个布尔）、
面板 `scripts/picker.js`（星标、状态点、列头开关、排序与筛选）、
`scripts/settings.js`（开关进只读删除名单）、`styles/app.css`（三态与星标，两套主题）。

审批策略、撤销语义、工具与视觉两条回退链都不变。开关默认关闭；老用户升级后行为的
唯一变化是名单优先排序，而升级时名单是空的，所以选择器逐字不变。
