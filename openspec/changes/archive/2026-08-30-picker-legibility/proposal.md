# 提案：判定要一眼看得见，次要说明收进悬停

## 问题

### 一、结论画得太小，等于没画

判定落在模型名之前一个 7px 的点上（`.picker-availability-dot`，`app.css`）。
点会变色——绿、红、空心——但紧挨着它的模型名始终是 `var(--text)`，可用与不可用
逐字同色。用户的原话是「现在不够明显，默认黑色，能用的也是黑色」。

行上确实还有一句结论文字（`能用` / `报错说没这个模型`，`picker.js` 的 `verdictHint`），
但它是 10px 的弱化色小字，且让每一行都变成两行——而这一列要装的是几十个模型。
于是这句字既没让结论变明显，又把列表的密度砍掉一半。

### 二、档位列窄到装不下自己

浮层左右分栏，模型段 62%、档位段 38%（`.picker-col` / `.picker-col-thinking`）。
浮层下限 260px，去掉边框与内边距后档位段只有一百出头：

- `Minimal` 七个字符加上「当前模型会降级」这句说明，必然折行
- 每档的说明是十几个字，摊在行上就是七行小字

用户的原话是「思考等级的宽度现在太窄了」「最好一行一个」。

### 三、每行一个按钮，这一列就是按钮墙

「试一下」只对没有判定的模型显示，但**没有判定的往往就是大多数**——这个入口本来
就是为「从没用过的模型」造的。于是常见情形是几十行里几十个按钮，而它是偶尔才用
一次的动作。用户的原话是「试一下可以藏着，鼠标移动的模型名称上悬浮显示」。

## 改动

### 判定落在模型名上

行本身带 `is-available` / `is-unavailable` / `is-probing`，由 CSS 给模型名上色：

| 三态 | 模型名 | 点 |
| --- | --- | --- |
| 可用 | 常规字色 | 实心绿 |
| 不可用 | **红**（`var(--error)`） | 实心红 |
| 未确认 | 常规字色 | 空心描边 |
| 正在确认 | 弱化色 | 琥珀描边并闪动 |

**可用不上绿**：`--accent` 已经是当前选中项的颜色（`.picker-item.is-active` 的名字
就是绿的），两处都用绿会分不清「这个能用」与「现在用的是这个」。需要一眼看见的是
哪几个不能用，而「不能用」在这个控件里此前没有任何醒目的表达。

摘要行的不可用也从琥珀改成红（`.picker-model.is-unavailable` 原本用 `--warn-fg`）：
同一件事在摘要行与列表里换个颜色，用户要学两遍。琥珀在这个控件里已经归「会降级」用了。

三态的结论文字随之收进行的悬停说明，行上不再为每个模型多占一行。**「正在确认」
仍然留在行上**——那一态没有颜色可依（名字是弱化色），而它正是「慢网关」与
「点了没反应」的唯一分辨依据，这一条是一期二期都明写过的。

### 浮层竖着分两段

模型段在上、档位段在下，各占整个浮层的宽度。浮层下限从 260px 抬到 300px。

代价是浮层变高，而它是**向上**弹的（控件在面板底部），超出视口顶端的部分会被
`overflow: hidden` 静默裁掉、连滚动条都不留。因此：

- 浮层限总高 `min(60vh, calc(100vh - 132px))`。取两条里更紧的那个：只靠减法不行，
  输入框会随内容长到 200px，那时触发按钮离视口底更远、浮层可用高度更小，
  而减法里的常数是固定的。
- 视口矮时压缩先落在模型段（它本就可滚动），压到 80px 下限后才轮到档位段让高度。
  两段都能滚，谁都不会被压到看不见。
- 宽度下限写成 `min(300px, calc(100vw - 24px))`：**CSS 里 `min-width` 永远赢过
  `max-width`**，写死 300px 时把面板拖到 300px 出头，浮层就比面板宽出十几像素，
  右侧被静默裁掉。这一条是本次在真实渲染器里量出来的，不是推演的。

### 档位一行一档

档位名在左、「会降级」短标在右，不折行。每档的用途说明收进悬停。

**降级标注不收进悬停**：它不是解释，是「你选的这一档在当前模型上不会生效」，
属于必须先看见才能做对选择的信息。一期的规格里「标注永不隐藏」是对模型写的，
这一条对档位同样成立。

### 「试一下」悬停才浮出

绝对定位压在行的右端（星标左侧），默认 `opacity: 0` 且 `pointer-events: none`，
悬停这一行或行内任意元素拿到焦点（`:focus-within`）时显形。

- **不用 `display: none`**：那会让按钮浮出时行宽改变，长模型名当场重新折行，整列跳一下。
- **仍留在 DOM 里且可聚焦**：键盘用户 Tab 得到，宿主的端到端驱动也仍找得到并 click
  （合成点击不做命中测试）。
- **没有悬停的设备上常显**（`@media (hover: none)`）：触屏没有「停上去」这个动作，
  藏在悬停后面等于这个入口不存在。

## 验证途径

这一屏的每条改动都只有排版后才成立，而假 DOM 没有计算样式、CSS 静态检查也看不出
`var()` 究竟取到了值还是静默退回默认色。因此新增 `PaneHarness --picker`：在真实
WebView2 里注入一份三态齐全的模型列表，量算出来的颜色、行高、行宽、`opacity`
与浮层的四条边，并在两套主题下各跑一遍。窗口尺寸可指定——`min-width` 与
`max-height` 都只在极端尺寸下暴露问题，常见宽度下量出来永远是「没出界」。

这条通路当场抓到了上面那个 `min-width` 赢过 `max-width` 的缺陷，而 Node 侧的
静态检查与假 DOM 单测当时全绿。

## 影响范围

面板 `scripts/picker.js`（判定 class、结论进 title、档位行改一行一档）、
`index.html`（两段改竖排、档位列头加「悬停看说明」）、
`styles/app.css`（模型名上色、档位行排布、降级标注、「试一下」的显隐、浮层限高限宽）。

`TaskPaneControl.cs` 的端到端钩子：`verdict:` 改报 `状态=/标记=/行内=/悬停=` 的字段形式
（此前裸报状态值，而「可用」是「不可用」的子串，断言可用会在其实不可用时通过），
新增 `probe-visible:`、`thinking-row:`、`name-color:`、`pop-geometry`、`seed-demo`、`manual:`。

判定的口径、探测的请求形态、名单与开关的行为、三态的含义都不动。
