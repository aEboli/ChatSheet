# 提案：按模型能力回退

## 问题

加载项对每个模型都发同一种请求：四种协议一律附带 17 个工具的函数声明
（约 2100 token），图片一律塞进多模态字段。这假定了「所有模型都能调用工具、
都能看图」，而实际用的模型并不都具备这两项能力。

**工具。** 不具备工具能力的模型有两种表现，都不好收场：

- 服务端以 400 拒绝带 `tools` 的请求。整轮直接失败，用户只看到一条接口错误，
  而问题其实是「这个模型不能这么用」。
- 服务端接受但模型不会用。它看着 2100 token 的工具声明，回一句
  「我无法访问你的表格」。`SystemPrompt.cs:25` 已经记下这个实测现象
  （DeepSeek-V4-Flash），当时的处置是把「你已经连上工作簿」写到系统提示最前面。
  那是在与症状周旋：声明发过去了，模型就是不发工具调用。

**视觉。** `ImageSupport.ProtocolSupportsImages` 直接 `return true`，注释写明
「具体模型可能不支持——那只能等服务端报错」。于是用户贴一张截图，得到的是一条
原始 400，而不是「这个模型看不了图」。更糟的情况是服务端不报错、静默忽略图片，
模型对着不存在的内容作答。

共同的根子是：加载项没有「这个模型能做什么」这个概念，因此既无法回退，
也无法告知。

## 改动

引入按「连接 + 模型」判定的能力档案，两条回退链各自成立。

### 工具：原生 → 文本协议 → 顾问

`ToolProtocolMode` 三档，按需降级，降级点都有面板提示：

**Native**（默认）走现有的函数声明。

**Text** 不再发 `tools` 字段，改为把工具清单写进系统提示，约定模型用围栏代码块
发出调用：

````
```chatsheet:tool
{"tool": "write_values", "args": {"range": "A1:B1", "values": [["名称", "数量"]]}}
```
````

清单用紧凑签名（`write_values(range, values, sheet?)` 加一行说明）而非完整
JSON Schema：弱模型读不动嵌套 schema，而紧凑签名只占约 700 token，是原来的三分之一。
解析出的调用走与原生调用完全相同的链路——同一套审批、同一套执行、同一套撤销记录，
因此文本协议不会绕过任何权限边界。工具结果以 `user` 消息回灌（文本协议下没有
`tool_call_id` 可用），并标记为工具结果，使上下文压缩仍能把它们当成首要压缩对象。

指令块不进对话气泡：流式输出经过一道闸门，识别到围栏开头就先攥住，
确认是工具块就整块吞掉，不是就原样放行。用户看到的是操作卡片，与原生模式一致。

**None**（顾问模式）连指令块都写不对时启用：不带工具声明，系统提示改写为
「你看不到也改不了工作簿，只能给出方案、公式与操作步骤」。这是为了防止最坏情况——
模型既不会调用工具，又被提示反复告知「你已经连上工作簿」，于是编造自己完成了操作。

进入 Text 的两条触发路径：

- 服务端以 400 拒绝且错误文本指向工具字段（`tools`、`function`、`tool_choice`）。
- 首步在 Native 模式下零工具调用，且正文出现「无法访问/看不到/没有权限」这类
  推辞。此时重跑该步，不消耗步数。这条启发式只在每个连接+模型的首轮试一次，
  判断错的代价是多跑一步。

### 视觉：中转 → 去图

服务端以 400 拒绝且错误文本指向图片字段时，记下该模型没有视觉能力，然后：

- **配了视觉中转模型**：把每张图单独发给中转模型（同一套连接与密钥，只换模型名），
  要求它按表格用途描述——结构、表头、可见数值、报错文案。描述以文本替换原图
  进入上下文，主模型据此作答。描述按图缓存，重试与后续轮次不重复付费。
- **没配**：去掉图片重发这一轮，并在消息里告知模型「用户附了图但你看不到」，
  面板同时提示用户可以换模型或配置中转。

不做的事：不在本地做 OCR（要引依赖且对表格截图效果不稳），不猜测哪些模型有视觉
（模型名与能力没有可靠对应关系）。

### 手动指定

设置页新增两项，都在「高级参数」里：

- 工具协议：自动探测（默认）/ 原生 / 文本指令 / 不用工具。
- 视觉中转模型：留空表示不启用。

手动指定的意义在于服务端不报错的那些情形——静默忽略工具或图片时探测无从触发，
用户比探测更早知道真相。

## 影响范围

新增 `Providers/ModelCapabilities.cs`（能力档案与缓存、错误分类）、
`Providers/TextToolProtocol.cs`（清单文本、指令块解析、流式闸门）、
`Providers/VisionRelay.cs`（图片转述）。

改 `Agent/AgentRunner.cs`（按能力构造请求、两条回退链、指令块执行）、
`Agent/SystemPrompt.cs`（三种模式的提示变体）、`Agent/Conversation.cs`
（文本协议下的工具结果标记）、`Providers/ChatTypes.cs`、`Storage/Settings.cs`
（两个新设置项）、`Bridge/AgentChannels.cs`（下发与保存新设置）、
面板 `chat.js`（两条回退提示）与 `settings.js`（两个新控件）。

工具清单、权限边界、审批策略、撤销语义都不变：文本协议解析出的调用与原生调用
经过同一条执行链路。原生模式的行为逐字不变——能力探测只在失败或推辞后介入。
