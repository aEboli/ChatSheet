## Context

见 `proposal.md`。功能区由嵌入的 Ribbon XML 声明，回调经 `ComAddIn` 的 `IReflect` 分派。现有适配入口位于 WebView2 面板内，前端 `runFit` 负责建立手动操作卡片，再通过 `sheet.fit` 调用宿主并接上撤销记录。

冷启动是关键约束：创建面板后，WebView2 环境、页面和模块脚本均为异步初始化。功能区回调若立刻查找 DOM 按钮，首次点击会在页面出现前丢失。

## Goals / Non-Goals

**Goals:**

- 功能区按钮成为现有适配能力的可靠快捷入口。
- 复用已有对齐选择、操作卡片、错误反馈与撤销链路。
- 冷启动点击在页面完全加载后执行一次。

**Non-Goals:**

- 不新增第二套 `fit_range` 执行逻辑或新的消息协议。
- 不移除面板内的适配入口，也不把其他表格工具提前加入快捷区。
- 不改变适配范围、对齐规则、审批或撤销语义。

## Decisions

### 在现有组尾部追加按钮

“适配当前表”直接跟在“诊断”之后，继续使用现有 `ChatSheetGroup`。另建一个只有单个按钮的组会在当前阶段增加无意义的视觉分割；今后快捷项增多时再按真实功能分类。

### 通过面板按钮触发现有前端流程

功能区回调先显示面板并导航到对话页，再由 `TaskPaneControl` 触发 DOM 中现有的适配按钮。这样自然沿用面板会话里记住的水平对齐，并由 `runFit` 生成同一张手动操作卡片。

备选方案是在 C# 回调中直接调用 `fit_range`。该方案虽少一次前端转发，却会绕过操作卡片与撤销入口，并需要重新实现结果反馈，因此不采用。

### 以页面加载完成事件释放待执行动作

`TaskPaneControl` 在导航开始时标记页面未就绪，在 WebView2 `NavigationCompleted` 成功后标记就绪。功能区在未就绪时只登记一项待执行适配；页面就绪后调用 DOM 按钮并清掉待执行标记。WebView2 官方程序集文档说明该事件在 `body.onload` 后触发，因此此时模块脚本已完成按钮绑定。

使用一个布尔待执行标记会合并页面加载期间的重复点击。这是刻意的：同一张表连续适配多次没有新增效果，避免首次加载时连点造成多张重复操作卡片。

## Risks / Trade-offs

- [Ribbon XML 回调名拼错会静默失效] → 用静态测试同时核对按钮声明、顺序、回调名及 C# 入口，并由现有 `IReflect` 日志兜底。
- [面板冷启动时 DOM 尚不存在] → 在 `NavigationCompleted` 前只排队，不直接执行脚本。
- [面板当前选择了非居中对齐但功能区看不出状态] → 快捷入口明确复用同一动作和会话选择；首次使用仍为居中，详细状态继续由面板按钮的说明呈现。

## Migration Plan

正常构建并重新安装加载项后，宿主重载 Ribbon XML 即出现新按钮。回滚只需移除按钮声明与对应转发方法，不涉及设置或数据迁移。
